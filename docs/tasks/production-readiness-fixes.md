# Production readiness quick fixes

## Intent and acceptance

Close the locally fixable preparation gaps from `docs/production-readiness.html` without changing
application behavior:

1. Committed `FEATURES.md` fails `prettier --check`, which stops `./scripts/verify` in CI at the
   first step. Format it; content must stay identical.
2. On Windows with `core.autocrlf=true` the working copy gets CRLF endings, so `format:check`,
   `design-system:check` (kit hashes) and `verify:packet` (CSV bytes) fail locally. Add
   `.gitattributes` forcing LF and refresh the working copy; `./scripts/verify` must pass on Windows.
3. Add `docs/release.md` with a post-publication smoke check, rollback, recovery before a session
   and error capture for the planned GitHub Pages hosting.

4. Add `.github/workflows/pages.yml`: on push to `main` (or manual run) verify with
   `./scripts/verify` and deploy `dist/` to GitHub Pages; publish nothing if the gate fails.

Out of scope: the owner decisions (repository visibility, session data rule, incident owner) and
switching the repository's Pages source to GitHub Actions, which only the owner can do.

## Validation

- `FEATURES.md`: Prettier only re-aligned table padding (`git diff --ignore-all-space` shows no
  content change). The behavior register was reviewed and needs no entry: no behavior changed.
- `.gitattributes` (`* text=auto eol=lf`): all 214 tracked text files now check out with LF;
  the index was already LF, so no committed content changes.
- The running Vite dev server created a `.vite/` dependency cache in the repository root, which
  broke `format:check` and `lint`. Added `.vite/` to `.gitignore` (Prettier honors it) and
  `.vite/**` to the ESLint ignores.
- `docs/production-readiness.html` is generated by the readiness renderer, so it is listed in
  `.prettierignore`.
- `./scripts/verify` passed on Windows 11 with Node 24.20.0: formatting, 67-file kit and
  reference checks, lint, types, 89 unit tests, 120-journey packet, build and 38 Chromium
  journeys. Not verified in CI yet.
- `pages.yml` follows the official custom-workflow pattern (docs.github.com, read 2026-11-14):
  `actions/configure-pages@v5`, `actions/upload-pages-artifact@v4`, `actions/deploy-pages@v4`,
  deploy job with `pages: write` and `id-token: write`, environment `github-pages`. Checked locally
  for YAML formatting only; it has not run on GitHub.
